Запрещено включать esp_lvgl_adapter, второй экземпляр LVGL либо слой, маскирующий LVGL 9 под LVGL 8. Не разрабатывать параллельно две полноценные реализации UI. Перевести существующий проверочный UI на API LVGL 8; в частности, заменить зависимости от lv_display_t/lv_image_* и других LVGL9-only API соответствующими API выбранной версии, проверяя реальные заголовки. Ассеты и image/font descriptors генерировать под LVGL 8; несовместимые бинарные форматы LVGL 9 не использовать.

## 4. Состав модуля и направления зависимостей

Рекомендуемые границы (точные имена можно минимально согласовать с уже созданным проектом):

- `kitchen_core`: состояния/сценарии/команды, независимые от LVGL, BSP и app_manager. На первом этапе достаточно минимального состояния и проверочного сценария, без выдуманной продуктовой функциональности.
- `kitchen_ui`: LVGL 8-представление, создаваемое в переданном контейнере; получает состояние и callbacks.
- `kitchen_app`: тонкая реализация app_descriptor_t/app_interface_t актуального хоста; предоставляет публичный getter дескриптора с C linkage, например `get_kitchen_app_desc()`.
- `kitchen_platform`: минимальные инъецируемые операции времени, UI dispatch, lock/unlock, навигации и при необходимости хранения; C-совместимые структуры, без передачи приватных типов хоста.
- standalone runner: отдельный стенд с app_main, BSP, esp_lvgl_port и источниками тестовых событий. Его компоненты не попадают в embedded dependency closure.

Не создавать все прослойки формально, если достаточно меньшего числа файлов с теми же границами. Не переносить кухонную логику в main, BSP или общий app_manager.

Публичный UI-контракт не включает framebuffer, DSI, аппаратные GPIO, lv_disp_drv_t и приватные структуры хоста. Заимствованный parent имеет ограниченный срок жизни. Доменное состояние не хранится внутри lv_obj_t/user_data как единственное хранилище.

## 5. Контракт встраивания и lifecycle

Реализовать существующий app_interface_t без изменений его заголовка. Учитывать create/destroy, start/stop, pause/resume, minimize/restore, create_content(self, container, view_type), on_before_suspend/resume/close/back и on_view_change. Для необязательных callbacks допустим NULL, если это действительно поддержано вызывающим кодом. Не добавлять новые требования к хостовому ABI.

В первой версии достаточно fullscreen UI. Widget capability выключить, если виджет не реализован. Не объявлять can_background/can_suspend без определённого поведения.

Parent-контейнер создаётся и удаляется app_manager. Kitchen создаёт/удаляет только свои дочерние объекты; нельзя удалять borrowed parent, менять screen целиком через lv_scr_load или самостоятельно возвращать чужие экраны. Проследить реальный порядок callbacks и удаления контейнеров в app_manager: очистка должна работать и при внешнем удалении parent, без double-free. Не предполагать, что stop, destroy и удаление LVGL-объектов всегда идут в удобном порядке.

При скрытии/минимизации UI прекратить ненужную перерисовку; фоновые операции разрешаются отдельно от активности представления. При stop/destroy отменить таймеры, анимации, подписки и отложенные UI-вызовы. Очередь события с устаревшим instance/view generation не должна обращаться к освобождённому объекту. Повторное открытие не создаёт дублирующиеся tasks/subscriptions.

Навигационные действия направлять существующему app_manager через публичные intents. Не захватывать глобальный touch, аппаратные кнопки, sleep и маршрутизацию Home Assistant.

## 6. Единственный владелец системных ресурсов

В embedded-режиме хост владеет:

- app_main, LVGL task/tick, дисплеем, touch, framebuffer и GUI-lock;
- backlight, глобальными яркостью и sleep/wake;
- Wi-Fi/C6, esp_event/default loop, NVS, настройками, файловой системой;
- HA webview/WebSocket sessions, TLS/certificate policies;
- аудио, Opus, I2S, микрофоном, доступом к capture и пользовательскими разрешениями;
- OTA, secure boot, flash encryption, partition layout, watchdog/power policies.

Kitchen не вызывает повторно lv_init, esp_lvgl_port init, BSP display start, Wi-Fi init, nvs_flash_init/erase или регистрацию глобального default event loop. Не выделяет вторую пару LCD framebuffer. Не изменяет sdkconfig/partitions/компонентные версии хоста и не создаёт конкурирующие driver handles.

Самостоятельный стенд может владеть BSP и дисплеем, но только за пределами embedded-компонентов. Его тестовые яркость/палитра/диагностика остаются функциями стенда, а не вмешательством кухонного приложения в глобальную яркость.

Микрофон и playback в актуальном снимке — существующие сервисы. Kitchen не открывает PDM/I2S и не запускает собственный захват. Если позднее потребуется голосовой интерфейс, это отдельное ТЗ на использование доступного публичного API/маршрутизации с сохранением permissions. Если API не предоставляет нужную возможность, пометить её недоступной; не расширять хост в рамках этого задания.

## 7. Потоки, lock и неблокирующие callbacks

Проверить, какие callbacks app_manager выполняются в GUI/job context и с какой блокировкой. Не брать нерекурсивный lock повторно внутри уже заблокированного контекста. Из других задач отправлять события через согласованный UI dispatch либо брать предоставленный хостом lock.

Контракт kitchen_platform должен однозначно определять тип результата lock и единицы timeout. Не смешивать bool bsp_display_lock с esp_err_t/ESP_OK — нормализовать только в host bridge. Публичный embedded-код не вызывает самостоятельную блокировку от esp_lvgl_adapter.

Не выполнять сетевые запросы, ожидание очередей, длительную запись flash или joins tasks под GUI-lock и в UI callbacks. При teardown не ждать task, которая сама ждёт удерживаемую блокировку. Задать лимиты очередей и payload; не передавать указатель на временное событие в асинхронный callback.

## 8. Home Assistant и продуктовая логика

Текущий home_assistant-компонент содержит webview/поток изображения и аудио; наличие этого компонента не считать готовым API состояний HA entities или service calls.

До отдельного ТЗ кухонный модуль работает на локальной модели с явным тестовым provider. Не создавать второй HA login, не хранить копии паролей/токенов и не открывать собственный WebSocket на предположении, что он необходим. Определить минимальные события/команды provider только по реальным потребностям UI; тестовые данные обозначать как demo.

Если необходимо постоянное хранение локальных kitchen-настроек, использовать предоставленный storage backend/отдельное согласованное NVS namespace, не пересоздавать системное хранилище. Не сохранять креды и не логировать их.

## 9. Аппаратные профили и ограничения встраивания

Сохранить HW V1.0–V1.3 и отдельные silicon-ветки как возможность самостоятельного стенда. Источники: WarehouseFlow, проект коллеги и рабочий Leader для V1.1/V1.2, как описано в исходном ТЗ. Проверка схем V1.1/V1.2 не вводится повторно как обязательное условие.

В embedded-режиме hardware profile и silicon определяет исключительно хост. Компонент kitchen не выбирает GPIO и не меняет DSI timings. Наличие standalone-профиля V1.3 не делает неизменённый crow-ha-fw совместимым с V1.3: если BSP хоста не поддерживает эту плату, это внешнее ограничение. Kitchen не должен пытаться исправить его поздней переинициализацией LCD.

## 10. Что означает «crow-ha-fw не меняем»

На этом этапе не изменять ни актуальный снимок Downloads, ни старый checkout crow-ha-fw. Разрабатывать компонент и стенд только в kitchen-addon. Подготовить INTEGRATION.md с точным описанием будущего подключения и ограничениями.

Факт: main/main.cpp актуального хоста явно вызывает app_manager_register для фиксированного списка приложений. Надёжного автоматического discovery в проверенных местах нет. Поэтому добавление папки компонента само по себе не означает появления кухонного приложения в меню.

Не использовать C++ static constructors, linker tricks, подмену существующего get_*_app_desc и скрытые hooks для обхода явной регистрации. В INTEGRATION.md привести минимальный пример include/getter/app_manager_register и CMake dependency для будущего интегратора, но не применять его к хосту. При требовании абсолютно нулевых изменений даже точки регистрации итог называется «совместимый подготовленный компонент», а не «интегрированное приложение».

Не копировать реализацию app_manager ради новой независимой платформы. Для проверки kitchen_app можно использовать минимальный test fixture, вызывающий нужные callbacks по реальному ABI; такой fixture не заменяет проверку полного хоста. Заголовки контракта предоставлять тестовому стенду явно, без абсолютных Downloads-путей в deliverable; при поставке копии учитывать лицензию и хранить reference hash, не изменять ABI.

## 11. Память и flash

В хосте существуют framebuffer, JPEG buffers, WebSocket/TLS stacks, Opus и microphone buffers. Самостоятельный kitchen memory PASS не является оценкой совместного режима.

В standalone проверить память до create, после open, после close и после повторных циклов. В embedded-компоненте не создавать аппаратные framebuffer; учитывать только kitchen objects/assets/core/queues. Задачи добавлять только при необходимости, с измеряемым размером стека.

Разметка хоста имеет два app slot по 0x680000, т.е. 6.5 MiB. Не увеличивать слоты и не занимать storage/sec_storage/nvs_key ради kitchen. По будущему пользовательскому build-отчёту вычислить реальный прирост signed image и запас, без переноса старых размеров/процентов из README как текущих фактов. Не менять signing/encryption и не копировать keys.

## 12. План корректировки существующего kitchen baseline

1. Зафиксировать контрактный snapshot c3675d87075 и hashes исходных заголовков/lock.
2. Перевести standalone SDK на 6.0.2, LVGL на 8.4.0 и графический порт на esp_lvgl_port 2.8.0~1; зависимости LCD/touch — по таблице хоста. Синхронизировать документы и инструкции. Существующий LVGL9-only код адаптировать минимально, а не оставлять подключённым параллельно.

4. Сохранить простой проверочный UI, добавить повторное создание/удаление и имитацию hide/suspend/resume/back. Новую полноценную кухонную функциональность не разрабатывать в рамках baseline.
5. Подготовить INTEGRATION.md, список заимствованных контрактов, матрицу статических и ручных проверок.
6. Пользователь выполняет standalone-сборку и предоставляет вывод. Нужные исправления выполняются по реальным ошибкам.
7. Полная интеграционная сборка/проверка на хосте — отдельный этап после разрешения на минимальное подключение приложения. Пока он не выполнен, статус только component-ready/standalone-tested с перечислением доказательств.

## 13. Документы и критерии завершения

Обновить при реализации README.md, ARCHITECTURE.md, BUILDING.md, VALIDATION.md, SOURCES.md и применимые манифесты; исходный BASELINE_SPEC.md привести к согласованному состоянию или явно пометить superseded. Не оставлять две равноправные взаимоисключающие версии стека.

BUILDING.md должен содержать точные команды пользователя с `/Users/sonyakuks/esp/esp-idf-v6.0.2/export.sh`, отдельными build-каталогами и новыми generated sdkconfig. Перед сборкой проверить idf.py --version. Не использовать существующие build-каталоги LVGL9-стенда. Не выдумывать dependencies.lock.

Подготовка исходников завершена, когда:

- kitchen UI использует LVGL 8.4 и модуль не требует миграции хоста;
- core отделён от LVGL/железа, descriptor соответствует ABI актуального app_manager;
- standalone и embedded dependency closure разделены, отсутствует повторная аппаратная инициализация;
- ресурсы, parent ownership, timers, dispatch и teardown описаны и просмотрены статически;
- есть явный план регистрации и открытый статус полной интеграции;
- весь crow-ha-fw остался неизменённым.

Ручная standalone-проверка: успешная сборка пользователя, изображение/touch, не менее 20 open/close циклов и 20 hide/show циклов, имитация suspend/resume, отсутствие callbacks после уничтожения и потери памяти на сравнимых стадиях. Аппаратная проверка по каждой доступной плате, без заявления квалификации отсутствующих панелей.

Будущая интеграционная проверка отдельно: переключение HA↔kitchen, back/minimize, sleep/wake, изменение Wi-Fi, одновременные HA video/audio/microphone sessions в пределах разрешённого поведения, отсутствие влияния на host brightness/settings/OTA и общий memory/flash budget. Не заявлять PASS этих пунктов по test fixture или отдельной прошивке.
