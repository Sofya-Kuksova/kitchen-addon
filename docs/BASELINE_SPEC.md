В корневом компонентном манифесте закрепить стек точно. Использовать один LVGL-адаптер; не подключать одновременно esp_lvgl_adapter и esp_lvgl_port. Не переносить компоненты вручную в managed_components. Не включать необязательные шрифтовые движки, декодеры и файловые мосты без использования.

После первой выполненной пользователем успешной резолюции/сборки проверить и сохранить полученный dependencies.lock. Не писать lock вручную, не подменять его lock-файлом примера. При несовместимости версии не менять молча: описать ошибку и предложить конкретную замену.

Ресурсы DSI/LDO/I2C/touch сохранять на весь срок использования; предусмотреть контролируемую обработку ошибок частичной инициализации. Не добавлять циклическую повторную аллокацию framebuffer.

### 5.1. Три независимые оси

Разделить board revision, LCD-параметры и silicon revision. Не выводить ревизию кристалла из номера PCB. Проверять допустимые сочетания в Kconfig/на этапе конфигурации, а не молча выбирать произвольный профиль. Не писать собственное автоопределение PCB без надёжного аппаратного признака.

Пример состава: `sdkconfig.defaults;config/board-v1.3.defaults;config/lcd-v1.3.defaults;config/silicon-v3.defaults`.

### 5.3. Ревизии кристалла

Подготовить отдельные silicon-профили для P4 <3.0 и P4 v3.x. В legacy явно задавать CONFIG_ESP32P4_SELECTS_REV_LESS_V3=y; для v3.x выключать. Минимальную поддерживаемую ревизию задать по реальным логам/целевым устройствам; не исключить старые 0.x автоматически выбором min=1.0. Список допустимых silicon revisions документировать.

Источник DSI PHY clock выбирать по целевой silicon-ветке; в проекте коллеги используются DEFAULT_LEGACY для <3.0 и DEFAULT для >=3.0. Имена и доступность сверить с IDF 6.0.3.

CPU/PSRAM вынести в silicon defaults. 360 MHz/200 MHz из старого примера и 400 MHz/250 MHz из сохранённого sdkconfig коллеги — опорные значения для соответствующих конфигураций, а не обязательные частоты любой платы. Проверить тип памяти/напряжение/допустимые частоты по устройству. Не включать 250 MHz глобально.

## 6. Графический baseline и память

Начальная конфигурация: RGB565, фиксированная ориентация 0°, DOUBLE_DIRECT, два framebuffer в PSRAM, программный рендеринг LVGL. Количество framebuffer вычислять/проверять API выбранного адаптера и передавать BSP; не создавать параллельно лишние полноэкранные LVGL-буферы.

Один кадр 1024×600 RGB565 занимает 1 228 800 байт; два — 2 457 600 байт, без объектов UI, декодеров, стека и промежуточных буферов. Проверять допустимые capabilities памяти и результаты выделений. Стек GUI первоначально держать во внутренней RAM. Не увеличивать stack/heap произвольно вместо анализа проблемы.

PPA-ускорение LVGL — отдельная выключенная по умолчанию опция. Не смешивать его с DMA2D передачи LCD: DMA2D оценивать отдельно по API IDF/драйвера. Не активировать сразу многопоточный draw, дополнительные framebuffer, rotation и ускорение без измерений. DOUBLE_FULL может быть отдельным сравнительным профилем для преимущественно полноэкранной перерисовки.

## 7. Проверочный UI и диагностика

Создать один простой экран с идентификаторами board/LCD/silicon-профиля и версии сборки, цветными участками RGB/белый/чёрный, текстом, движущимся объектом, индикацией координат/касания, угловыми touch-мишенями и регулировкой яркости. При яркости 0 должен существовать способ восстановления, например возврат тестовым таймером через несколько секунд.

Лог запуска: версии IDF/LVGL/adapter, выбранные профили и фактическая chip revision, размеры дисплея, параметры DSI и reset, CPU/PSRAM, framebuffer count, этапы инициализации и точные ошибки. Диагностика памяти: free/largest для internal и SPIRAM до/после запуска, GUI stack high-water mark. Обновление диагностических виджетов редкое и под lock; никаких логов на каждый пиксель/кадр. Идентификаторы пакета не должны выдавать кандидат за проверенное устройство.

## 10. Критерии приёмки

Подготовка исходников завершена, если профили четырёх PCB представлены без дублирования приложения, ревизия silicon выбирается отдельно, GPIO/ресурсы имеют явное владение, UI независим от PCB, версии закреплены, документация/команды/ограничения подготовлены, diff проверен. Это не означает build/device PASS.

Build PASS: пользователь предоставил успешный результат для конкретной комбинации, зависимости разрешились без неизвестных Kconfig/API, bootloader и app соответствуют target/revision и помещаются в разметку. В отчёте перечислить проверенные комбинации.

Device PASS отдельно для каждой реальной платы/диагонали/silicon: три холодных включения, три reset, стабильные цвета без сдвигов/разрывов, touch в четырёх углах и центре, яркость и восстановление после 0%, не менее 30 минут тестовых анимаций без reset/WDT/ошибок драйвера. Сравнить память после прогрева и в конце; не требовать произвольного FPS без согласованной сцены. Сохранить логи, фото и настройки.

Для HW V1.3 9″ и 10.1″ оформить отдельные результаты. Успех на одной диагонали не квалифицирует другую. Если нужных плат нет, baseline передаётся как source/build-ready с открытой аппаратной приёмкой.

## 11. Ограничения исполнителя

Не запускать сборку/компиляцию проекта, прошивку, монитор, esptool, OpenOCD/JTAG или аппаратные команды. Все firmware builds и device/runtime-проверки выполняет пользователь/тестировщик. Не запускать средства проверки, которые косвенно вызывают сборку.

Не изменять опорные проекты, generated/vendor/managed code. Не выполнять git commit/push, не создавать ветки и не менять историю без отдельного явного разрешения. Текущая задача автора ТЗ — только документ; реализация baseline начинается отдельным запросом.

В итоговом отчёте реализации перечислить изменённые файлы, выбранные версии, факты/предположения, выполненные статические проверки, команды пользователя, открытые build/device gates и Git status. Не сообщать, что совместимость подтверждена, если есть только исходники или успешная сборка.
